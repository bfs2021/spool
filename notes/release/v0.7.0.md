## What's Changed

**Loop health watchdog.** The hub now opens a problem, and tells the owner, when a loop's turn runs past a time limit, when a wake starts no turn, and when a message to a person goes undelivered past a grace period; each limit is a setting, and the Fleet page and the loop page say which it is and since when. The turn limit is checked outside the loop's own process, so a loop wedged mid-turn is reported too. (#1142–#1147, #1260: PRs #1245, #1246, #1248, #1255, #1258, #1267, #1268)

**Import from prompts.chat.** New loop fills itself from a prompts.chat bot URL: name, mission, runtime hint and the egress to allow, all editable before Create. New loop also imports a prompts.chat team: a preview lists the loops with their roles and handoffs and the channel they share, and Create makes them, each mission ending with its handoffs to the others. The hub fetches from prompts.chat only, on the operator's paste (ADR-0063). (#1262: PRs #1271, #1272, #1274, #1288, #1291)

**A person hears when a loop dropped their message.** A message the hub gives up on is answered with a drop notice in the chat it came from, and the control room says which loops dropped it. (#1205, #1238: PRs #1239, #1241)

**Cloud loops keep their session.** A cloud loop keeps one claude.ai session through a rotation and a stop, so neither leaves a stale session in the operator's account. (#1278, PR #1293)

**Fixes.**
- A claude that closed its output but kept running is ended instead of holding its loop deaf to ticks, messages, Pause and Kill. (#1247, PR #1252)
- One loop that stops reading its commands no longer holds every other loop's ticks. (#1259, PR #1261)
- A loop name or bot username that a mention already means is refused at create and rename, so no loop takes another's mentions. (#1273, PR #1279)
- A new bus kind reaches no member's stream until it is named as streamable. (#1240, PR #1253)
- Hub listeners take plain TCP, not Go's default multipath TCP. (#1250, PR #1251)
- A cloud loop's setup view never shows a check's result before the one that ended. (#1243, PR #1244)
- Disabled controls in the control room mute instead of fading. (#1275, #1277: PRs #1276, #1292)
- A login whose loops all run in the cloud no longer shows a plan cap as if it acted: the control room says its figures will not update, or that usage is unknown. (#1303, PR #1307)
- Signing a Claude login in on a hub running natively on macOS now works: the CLI opens no browser, the sign-in link is read even when the terminal wraps it, and the login stays out of the Keychain. (#1304, PR #1306)
- The setup walk of a cloud loop from before its environment was set saves the repo with the environment in one edit, instead of refusing the repo with a message about the environment. (#1286, PR #1309)
- `spool upgrade` now upgrades a hub no systemd unit runs, such as one started by hand on macOS: it backs up, installs and rolls back as the hub's own user, stops the hub, and asks you to start it again with the exact command. Its backup now works with the BSD tar macOS ships. (#1311, PR #1312)
- The Channels page no longer says no Telegram or Slack room carries a channel: it says a loop can bind its room to a channel on its own page. (#1317, PR #1318)

## Upgrading

Run `sudo spool upgrade v0.7.0` from v0.6.x on a hub a systemd unit runs. From v0.5.1, follow [docs/OPERATIONS.md → Upgrading](https://github.com/enes-alatas/spool/blob/v0.7.0/docs/OPERATIONS.md#upgrading) by hand.

A hub you started by hand, such as `./bin/spool` on a Mac, upgrades to v0.7.0 by hand as before, because the `spool upgrade` in a v0.6.x binary still needs a unit: stop the hub, back up its data directory, move the checkout to v0.7.0, run `make build` and `make image`, and start it again ([Upgrade](https://github.com/enes-alatas/spool/blob/v0.7.0/docs/OPERATIONS.md#upgrade)). From v0.7.0 on, run `./bin/spool upgrade --no-unit` as the user who runs the hub, without `sudo` ([A hub with no unit](https://github.com/enes-alatas/spool/blob/v0.7.0/docs/OPERATIONS.md#a-hub-with-no-unit)).

After the upgrade every cloud loop makes one new claude.ai session at its next resume or rotation, since its stored state carries no session to keep; from then on it keeps one.
